# 引き継ぐ判断

旧リポジトリで決めたことのうち、トライアルでも前提にしてよいもの。
トライアルで覆す根拠が出たら覆してよい。そのときはここを直す。

## 1. システム全体

| 判断 | 理由 |
|---|---|
| 固定側（検出・予測）と移動体（走行）を分け、目標座標だけで繋ぐ | 元作品の骨格。移動体を軽く単純にでき、それぞれ単独で試せる |
| カメラは固定し、移動体に載せない | 責務が混ざる。載せるならカメラ自身の動きの補正（IMU）が要る |
| 移動体の性能は最高速度ではなく「0.4 / 0.6 / 0.9 秒で何 m 動けるか」で見る | 移動に使える時間が 0.3〜1.0s しかない。最高速度に達する前に勝負が決まる |
| 測っていない数値を合否条件にしない | 想定値で合否を切ると、根拠の無い数字に設計が引っ張られる。目標値は実力を見てから決める |
| 最終の判定はキャッチ成功率だけ | 速度・遅延・精度は途中の目安。全部満たしても受け止められるとは限らない |
| 初期は投げる位置・方向を固定し、必要な横移動を小さくしてよい | 設計の一部として認める。待機位置の調整も同じ |
| 要るか分からない物は先回りして買わない | 緩衝材・非常停止の部品・上位の計算機などは、必要が分かってから買う |
| 演出（LED・音など）は後回し | 時間予算の役に立たない。いつでも足せる |

## 2. 固定側

| 判断 | 理由 |
|---|---|
| センサは RealSense D435 | グローバルシャッターで速く動く物に強い。Depth で直接 3D が取れる |
| 計算機は手元の Raspberry Pi 4 | 足りないと**測って**分かったときだけ、設定・ソフトの改善 → 計算機の変更の順で考える |
| 物体検出は軽い方法から試す（Depth 差分・背景差分・フレーム間差分など） | Pi 4 で AI モデルを最初から前提にしない |
| fps は「必要なサンプル数 ÷ 使える時間」から決める | 30fps で足りるなら 30fps でよい。60fps ありきにしない |
| 床平面は Depth から平面を当てはめて求める | D435 は IMU を持たない |
| 移動体へは目標座標と到達時刻だけを送る | 画像・Depth を送らない。途絶を検出するため、通し番号か時刻を付ける |

## 3. 移動体の機構

| 判断 | 理由 |
|---|---|
| 3輪オムニ、120°配置、部品から自作 | 丸いゴミ箱は向きを保つ必要が無いのでメカナムの利点が無い。オムニはモータの力を並進に無駄なく使える。3輪は軽く安く、3点で接地するのでゴミが落ちたときの重心移動に強い |
| 既製の全方向ベースは買わない | 安いものは 0.6 m/s 級で、結局モータを替えることになる |
| ゴミ箱本体は市販の軽量 PP 製（山田化学 No.335） | 全部を3Dプリントすると重く、時間がかかり、剛性も出ない |
| 3Dプリントするのは駆動ベース・ゴミ箱の固定具・受け口の漏斗・センサの固定具 | 金属の切削加工はしない |
| モータは付属の金属ブラケットで駆動ベースへ留める | 3Dプリント部品でモータ本体を挟むより、剛性・位置決め・交換のしやすさで勝る |
| ブラケットの取付穴は4つのうち、接線方向の2つだけを使う（2026-09-10） | 旧設計の形では、4穴を使うと内側の列がゴミ箱の固定具の下に入るなど、周りの部品と干渉したため。**ボルト2本で駆動ユニット1台を持たせてよいかは確かめていない**（機体の重さの 1/3、受け止めたゴミ、ストールトルク約 0.30N·m を受ける） |
| バッテリ・モータは最下部に置き、上部を軽くする | 低重心にして急加速・急停止で転ばないようにする |
| 造形部品は 180mm 以内に分割し、継ぎ目は貫通ボルト＋熱圧入インサートで留める | A1 mini の造形範囲。FDM は層の間が弱いので、樹脂には圧縮だけを掛け、ダボは位置決めにだけ使う |
| 配線は造形したガイドではなくテープで留める | CAD で組立を見て要らないと判断した（3部品・約120g）。ただし、ガイドがあれば形で防げた線の取り違えを、色や印で防ぐ必要がある |
| ホイールを浮かせる台は造形せず、木片や本で代用する | 旧設計の台は3部品・約733g で造形物全体の35%を占めていた。造形を待たずに済む。3つの高さを揃えること |
| 将来モータを替えるときも 6mm D シャフトのものを選ぶ | 手元のホイールとハブを使い続けられる |

## 4. 移動体の電気

| 判断 | 理由 |
|---|---|
| モータドライバは AE-TB67H450 を1モータに1台 | 安い。ストール電流に対して余裕が小さいので、ソフトのロック保護を必須とする |
| モータは LiPo からドライバへ直接。ロジックの 5V は BP5293-50 で作る | |
| メインヒューズは 10A をバッテリの直後に | 短絡・配線事故から LiPo と配線を守るため。モータ1個のストールは守らない（ソフトで守る） |
| エンコーダは 3.3V で動かす | ESP32 の GPIO が 3.3V 系。問題が出たときだけ 5V＋レベルシフタ |
| IN1 / IN2 を2本とも PWM で動かす（案B） | 部品を増やさず、前進と後進で同じ減り方になり、指令ゼロがストップになる。「PWM＋向き」で繋ぐと指令ゼロで全速逆転する |
| ドライバの定電流制御は切る（RS → GND、VREF → 3.3V）。机上では安定化電源の電流制限で守る | 手に入るセンス抵抗では上限が低すぎて走らず、挙動も見えなくなる |
| USB と BP5293-50 の 5V は JP1 で切り離す | 5V どうしの逆流を防ぐ。DevKit の版の違いを調べなくて済む |
| 接地は動力と信号に分け、星形に1点で合流させる | PWM のスパイクがエンコーダのカウント誤りになるのを防ぐ |
| 0.1µF はモータ端子・ドライバの VM と VREF・ADC 入力のすぐ近くに置く | 置き場所を外すと効かない |
| 最初の通電は安定化電源で、1段に1つずつ未知を増やす | → [circuit-bringup.md](./circuit-bringup.md) |
| MCU は classic ESP32 に固定する（S3 / C3 / C6 / H2 は不可） | DualSense は Bluetooth Classic でしかつながらない。Classic を持つのは無印 ESP32 だけ |

## 5. 移動体のソフト

| 判断 | 理由 |
|---|---|
| 制御は「逆運動学 → 各輪の速度 PID → PWM」。位置制御はその上 | 3輪120°の標準的な形 |
| 安全機能は走らせる前に入れる: ①モータロック保護 ②低電圧保護 ③PWM 上限 ④指令ウォッチドッグ | 手動で走らせるときがもう「外からの指令で機体が走る」最初の場面。④が無いと、コントローラの電池切れや切断の瞬間に最後の入力で走り続ける |
| ④は「最後に有効な指令からの経過時間」だけを見る形にする | 指令元をコントローラから固定側の通信へ差し替えても、同じ判定が使える |
| 固定側とつなぐ前に、動作領域の制限を入れる | 誤検出や予測の発散がそのまま暴走になる |
| ロック保護・低電圧の閾値は、決め打ちせず設定できる値にする | 電圧降下や電流は実機で測ってから決める。低電圧は移動平均・時間判定・ヒステリシスで、加速時の一時的な降下で止まらないようにする |
| エンコーダの分解能・ホイールの実効径をコードに決め打ちしない | 測って校正する。実効径（荷重でローラーが潰れる分）は、ずれると「予測は合っているのに届かない」という一番切り分けにくい形で出る |
| 足回りは最初に手動（DualSense）で動かす | 組み立て直後に起きるのは性能不足ではなく、極性・符号・輪の番号のずれ。自動計測ではこれを切り分けられない。手動の結果では性能を判定しない |
| DualSense は ESP32 へ Bluetooth Classic で直接つなぐ（第一候補） | PC も通信方式も切り分けの輪に入らない。ライブラリは Bluepad32。実機ではまだ試していない。だめなら PC 経由に切り替える |
| デッドマン（押している間だけ動く）と、接続が切れたら止まるを必須にする。速度は最初 30% 程度に絞る | ただし、どちらも無線に頼るので**安全装置ではない**。物理的な非常停止は別に要る |
| テレオペ用のファームと本番用のファームは別ビルドにし、同時に有効にしない | Bluetooth と Wi-Fi が 2.4GHz を時分割で使うので、同居させると制御が乱れる。加えて BTstack のライセンス（→ [dev-environment.md](./dev-environment.md#5-btstack-のライセンス)） |
| 性能が足りなくても、すぐ高いモータに替えない | 調べる順: スリップ → 電圧降下 → PWM / PID 設定 → 上部の重さ → 重心 → フレーム剛性 → 投げ方と必要な横移動 → バッテリ容量 → 最後にモータ |

## 6. シミュレーション

| 判断 | 理由 |
|---|---|
| 軌道シミュレータは「軌跡のアニメーション」より「間に合う／間に合わないの境界の図」を主にする | 投げ方をどう決めれば成り立つかを机の上で決めるのが目的 |
| 物理モデルは最小限から始める。含めない要因は結果に必ず明記する | 入っていないものが入っているように見える誤った安心を防ぐ |

旧シミュレータで含めたもの・含めなかったもの:

| | 含めた | 含めなかった |
|---|---|---|
| 投擲 | 空気抵抗なしの放物運動、投げ方のばらつき | 空気抵抗、回転（マグヌス効果）、跳ね返り |
| 観測 | 検出開始の遅れ、サンプリング周期、位置のノイズ、取りこぼし | センサ固有の歪み、視野外、遮蔽 |
| 移動体 | 加速度の上限、最高速度、減速 | スリップ、方向による性能差、逆運動学、PID |
| キャッチ | 位置と時刻 | 跳ね出し |

## 7. 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 100mm ホイール（Nexus 14049） | 60mm（Nexus 14145 相当品）にした |
| Pololu #1443（30:1、350RPM、64CPR、約1.5〜1.8万円） | 高い。まず JGB37-520 で測る。6mm D シャフトなので、将来の交換先としては有効 |
| BTS7960（43A）ドライバ | 試作には過剰 |
| 3S LiPo 2200〜3000mAh | 1500mAh 35C にした。容量が足りなければ見直す |
| 別売りのモータブラケット | モータ付属の金属ブラケットで足りる |
| 汎用の降圧コンバータ | BP5293-50 にした |
| RealSense D435i | IMU はカメラを動かす場合にしか要らない |
| Kinect v2（中古） | 安いが、Windows・専用 SDK が要り、サポートも終わっている |
| Luxonis OAK 系 | カメラ内で AI 処理できるが、今は要らない |
| メカナムホイール | 丸いゴミ箱では向きを保つ必要が無く、利点が無い |
| 外付けロジック（74HC00）で PWM＋向きを IN1/IN2 に変換 | IC が3個増える。案B で足りる |
| ROS 2（rviz / rosbag） | Pi 4 には重い。設計の参考にはする |
| Grafana + Prometheus | 1投擲を1件として扱う記録と相性が悪い |
| クラウドへの送信 | 屋内・1つのネットワークで完結する |
| ブラウザから非常停止する | Wi-Fi に頼る停止は安全装置にならない |
| FreeCAD だけで機構を設計する | 形状の正がバイナリ（`.FCStd`）になり、git で差分が読めない。面の参照番号が再計算で飛ぶ問題（トポロジカルネーミング）が未解決 |
